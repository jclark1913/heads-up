# Motion and platform feasibility

Research checked September 24, 2026. Documentation findings are not physical-device test results.

## Can a PWA access phone motion?

Yes. Web pages can receive `deviceorientation` and `devicemotion` events over HTTPS on compatible devices. Installing the PWA is not a prerequisite for using these browser APIs and does not confer native sensor privileges. Device orientation supplies attitude; device motion supplies acceleration and rotation rate. [MDN orientation guidance](https://developer.mozilla.org/en-US/docs/Web/API/Device_orientation_events/Detecting_device_orientation), [Apple DeviceMotionEvent documentation](https://developer.apple.com/documentation/webkitjs/devicemotionevent).

For this game, tilt relative to gravity is enough. GPS, a camera, a microphone, and a compass heading are unnecessary. The required delivery model is a PWA with a browser motion adapter. Build the small playable gesture MVP first, then validate it on the owner's Pixel 10a and iPhone 17 Pro before expanding the feature set. The [build plan](05-validation-and-delivery.md) separates a testable handoff from measured gesture acceptance.

## iOS and Android differences

**iOS Safari:** motion/orientation events are available. Treat the sensor request as an explicit permission flow initiated by a button tap. Feature-detect each relevant `requestPermission` method, handle rejection/denial, and verify useful readings afterward. Do not assume a remembered application preference means the browser still grants access. [MDN permission documentation](https://developer.mozilla.org/en-US/docs/Web/API/DeviceOrientationEvent/requestPermission_static), [motion permission documentation](https://developer.mozilla.org/en-US/docs/Web/API/DeviceMotionEvent/requestPermission_static).

**Android Chrome:** the events are available on suitable hardware. Permission behavior is version-dependent; do not hard-code “Android never asks.” Current MDN compatibility data lists `requestPermission()` starting in Chrome 152, while older versions lack that method. Feature detection must accommodate both behaviors. API presence alone does not prove hardware, permissions, or useful readings. [Orientation compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/DeviceOrientationEvent.json), [motion compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/DeviceMotionEvent.json).

**Screen orientation:** Safari does not currently implement `screen.orientation.lock()` according to compatibility data. Chrome Android supports it, with browser/context restrictions. Treat a landscape lock and fullscreen as enhancements. Provide a rotate-phone prompt and a layout that works without forced fullscreen; do not make successful locking a Start requirement. [Screen orientation compatibility](https://github.com/mdn/browser-compat-data/blob/main/api/ScreenOrientation.json), [lock restrictions](https://developer.mozilla.org/en-US/docs/Web/API/ScreenOrientation/lock).

**Keeping the display awake:** request a screen wake lock while preparing/playing, release it after the round, and handle release/rejection. WebKit specifically fixed wake lock in Home Screen web apps in Safari 18.4, so older installed iOS behavior must not be inferred from browser-tab behavior. Power settings can still prevent a lock. [WebKit Safari 18.4 release notes](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/), [Wake Lock API](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API).

**Sound and vibration:** start/resume audio from an explicit interaction and provide a sound test. Autoplay policy can block playback. `navigator.vibrate()` is available on Android Chrome but is not supported by Safari; vibration is optional reinforcement. [Autoplay guidance](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay), [vibration compatibility](https://github.com/mdn/browser-compat-data/blob/main/api/Navigator.json).

**Installation and browser containers:** test Safari tabs and iOS Home Screen launches separately, likewise Android tabs and installed launches. An install-prompt event is not universal, so supply browser-appropriate installation help. Embedded browsers and iframe previews are not initial support targets; link users to the top-level app in a supported browser. [Install prompt documentation](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeinstallprompt_event).

## Permission and readiness contract

**M-01 — Secure origin.** Production and physical-phone testing use trusted HTTPS at a top-level URL. A phone opening a development computer's plain HTTP LAN address is not the same as a localhost secure-context exception. Ensure hosting policy allows the app's own accelerometer/gyroscope access. [Device Orientation and Motion specification](https://www.w3.org/TR/orientation-event/).

**M-02 — Explicit request.** On Enable movement, check `isSecureContext` and whether the selected event interface exists. Invoke its permission method, if present, directly inside the tap handler before unrelated asynchronous work. If an experiment needs both streams, feature-detect each method independently and invoke needed requests during that same activation; do not await one dialog before initiating another request.

**M-03 — Readiness.** After access is allowed or no explicit method exists, subscribe and look for finite, usable samples. Readiness states are `checking`, `ready`, `denied`, `unavailable`, and `insecure-context`. An initial five-second no-data deadline begins after the permission promise resolves, not while the dialog is open. Offer a relevant Retry action and Enable buttons when readiness fails; buttons remain hidden until the user explicitly enables them. Missing/null values are not zero; zero is a valid angle.

**M-04 — Recovery.** Never repeatedly prompt automatically. A denied response offers Enable buttons without automatically changing the user's control setting, and offers a user-initiated retry, with browser-specific recovery help only after that behavior has been tested. Subscribe only during readiness checks, practice, preparation, and active play, including feedback while waiting for neutral. Clean up listeners on exit; verify data again after resuming.

## Gesture detector proposal

**M-05 — Physical meaning.** Neutral means the display is approximately vertical, facing clue-givers. Correct means tilt the display toward the floor. Pass means tilt it toward the ceiling. Return to neutral between actions. Support either landscape direction without reversing these meanings.

Do not threshold raw `beta` alone: sensor axes are tied to the device's natural coordinate frame, not the current layout orientation. Derive the elevation of the outward screen normal relative to horizontal from the orientation rotation, or from a validated gravity-vector estimate. Positive elevation means face-up, negative means face-down; neutral is near zero. Absolute compass heading is not needed. [Coordinate-frame specification](https://www.w3.org/TR/orientation-event/).

For the standard orientation convention, a candidate computation is `asin(clamp(cos(beta) * cos(gamma), -1, 1))`, with angle conversion between degrees and radians. This describes screen-normal elevation, not a raw Euler pitch. Validate the sign and usable ranges on real devices in both landscape directions. Do not silently substitute acceleration data without testing its sign and filtering separately.

**M-06 — Calibration.** Collect a stable near-vertical neutral pose while the preparation countdown runs; use an initial 500 ms stability window. Reject a flat phone as neutral. Proposed acceptable starting elevation is within 15 degrees of vertical, with a small measured spread. Store calibration only for the current practice/round and reset it after interruption. Do not continuously adapt neutral while a user is making a gesture.

**M-07 — Filtering and thresholds.** Start the playable MVP with light time-based smoothing and a 50-degree tilt from calibrated neutral, held for 120 ms, to recognize an action. Require a neutral return within 15 degrees for 200 ms before rearming. These are tuning values, not measured production settings. Use elapsed time, not frame counts. Clear a candidate if direction changes, data is invalid, or a sample gap is too large; a stalled sample cannot satisfy dwell time.

**M-08 — One gesture, one action.** Detector states are `uncalibrated`, `armed`, `candidate-correct`, `candidate-pass`, and `awaiting-neutral`. After emitting one action, enter `awaiting-neutral`; both elapsed feedback time and observed stable neutral are required to rearm. Continuing to hold a tilt, overshooting to the opposite direction, or bouncing around a threshold cannot answer a second prompt. Reset pending candidates on pause, mode change, expiry, or recalibration.

**M-09 — Stable presentation.** Stable landscape presentation is required for motion-controlled forehead gameplay, even when the browser cannot lock orientation. Verify usable landscape before starting; provide positioning or rotation-setting guidance if it is blocked. Keep the gameplay content in the chosen landscape direction through normal scoring tilts using the web layout. Keep the prompt hidden while tilted after an answer. Filter incidental viewport/orientation changes near a flat pose; pause only for sustained invalid playing posture. Validate with OS rotation lock on and off, browser chrome visible, and both ends of the phone pointing left. Unexpected portrait prompts or repeated interruption screens during normal flips fail the release gate; this behavior has not yet been validated.

The first playable MVP uses orientation-derived elevation; compare a filtered `accelerationIncludingGravity` approach if device testing shows a need. Pick one validated source per session. Source changes require disarming and recalibration. Generic Sensor APIs are not required for the MVP.

**M-10 — Browser guidance.** Show recovery advice for the actual failed capability, such as movement permission, missing sensor data, or an unusable landscape presentation. Do not show a blanket warning telling Safari users to install Chrome or Firefox. Their documented iPhone implementations also use Apple's WebKit; switching browser brands is therefore not a reliable remedy for a missing WebKit orientation API, although browser-specific permission/UI behavior can differ. [Chromium iOS architecture](https://chromium.googlesource.com/chromium/src/+/main/ios/web/), [Firefox iOS architecture](https://firefox-source-docs.mozilla.org/overview/ios.html). Recommend another browser only when testing shows that the specific OS/browser combination fixes the observed problem. Offer a full-browser launch when an embedded browser fails. Capability checks remain authoritative if alternative browser engines become available in a user's environment.

**M-11 — Detection and fallback flow.** Default to motion when there is no saved manual preference. If the user has enabled manual controls, skip sensor permission/calibration and render the manual layout. Otherwise:

1. Inspect secure context and sensor interface availability. Treat orientation-lock/fullscreen support as optional. Browser/version information can select a tested help message, but does not establish that motion works or fails.
2. Request movement access from a tap where required, then confirm useful readings and perform practice/calibration. Checks establish current readiness, not a guarantee against future failures.
3. If landscape is not usable, show “Hold your phone sideways.” If it remains in portrait, offer conditional guidance: “If the screen will not rotate, turn off Portrait Orientation Lock in Control Center, then hold the phone sideways.” The web API reports document orientation, not the iPhone's Control Center lock setting; do not claim to have detected that setting or attempt to change it. [Screen Orientation API](https://developer.mozilla.org/en-US/docs/Web/API/ScreenOrientation), [Apple rotation guidance](https://support.apple.com/en-in/118226).
4. Recheck after the user returns or taps Retry. Clear the guidance when usable landscape and sensor readiness are restored. Opening Control Center during a round follows the interruption rules.
5. Offer Enable buttons when a required capability is unavailable or a problem remains. Missing sensors or denied permission can go directly to that offer without making the user attempt unrelated fixes. The offer enables manual mode only when activated; declining it leaves motion selected. The setting is also available independently for accessibility and preference.

Observe required capabilities during motion play. If they fail, pause and offer recovery rather than silently switching input. Manual mode remains usable when landscape cannot be achieved. Never infer an OS rotation-lock setting solely from a portrait viewport, missing lock API, or browser name.

## Support policy and feasibility gate

The first trial targets the owner's iPhone 17 Pro with Safari and Pixel 10a with Chrome; their OS/browser versions will be recorded at test time. Validate tab and Home Screen/installed launch separately. These two devices establish an initial feasibility result, not broad certification. Release certification targets are Safari on iPhone in tab and Home Screen modes, and Chrome on Android in tab and installed modes. Include current stable releases at test time plus the oldest OS/browser combination the product intends to advertise. iOS 18.4+ is a proposed starting floor because of the installed wake-lock fix, not a claim that every later release is validated. Android's oldest supported version remains a decision pending available devices.

Other browsers, tablets, and embedded webviews can be offered the option to enable manual controls when needed; they are not promised motion support until tested. Publish exact tested device/OS/browser versions with results. If the playable MVP cannot make gestures and landscape presentation dependable on both target platforms, revise the web detector, layout, or setup flow and retest. Unresolved failures on a required platform block release. Manual controls are a fallback for unavailable or unwanted sensors, not a substitute for passing the core motion-gameplay gate. Native apps and wrappers are outside the chosen delivery model.
